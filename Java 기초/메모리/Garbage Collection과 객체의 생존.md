## 0. GC를 이해하기 위한 기본 개념

GC를 이해하려면 먼저 JVM 메모리와 객체 참조가 무엇인지 알아야 한다.

### JVM 메모리 영역 간단히 살펴보기

Java 프로그램이 실행될 때 JVM은 여러 메모리 영역을 사용한다. 모든 영역을 GC가 동일한 방식으로 관리하는 것은 아니다.

| 영역 | 저장되는 내용 | GC와의 관계 |
|---|---|---|
| Heap(힙) | `new` 등으로 생성한 객체와 배열 | 대부분의 객체가 할당되며 GC의 주요 관리 대상 |
| Java Stack(스택) | 메서드 호출 프레임, 지역 변수, 연산 중간 값 등 | 프레임에 있는 객체 참조가 GC Roots를 찾는 데 활용됨 |
| PC Register | 각 스레드가 현재 실행 중인 JVM 명령의 위치 | 실행 상태를 설명하는 영역 |
| Native Method Stack | 네이티브 메서드 실행에 필요한 정보 | JNI 등을 통해 유지되는 참조와 연관될 수 있음 |
| Method Area / Metaspace | 클래스 메타데이터 등 | 클래스 메타데이터 자체와 힙 객체의 생존 판단은 구분해야 함 |

- 객체 본체는 일반적으로 Heap에 생성된다.
- 지역 변수에 객체가 대입되었다고 해서 객체 본체가 스택으로 이동하는 것은 아니다. 지역 변수에는 객체를 가리키는 참조가 저장될 수 있다.
- 실제 참조가 스택, 레지스터 등 어디에 존재하는지는 JIT 최적화와 실행 상황에 따라 달라질 수 있다.
- Metaspace는 주로 클래스 메타데이터를 저장하는 영역이며, 일반적인 Java 객체가 저장되는 Heap과는 다르다.

> 🔗 힙 객체가 Metaspace의 클래스 메타데이터(Klass)를 어떻게 참조하는지는 [객체 메모리 구조 - HotSpot의 객체 표현](./HotSpot%20객체의%20메모리%20구조와%20할당.md#1-hotspot의-객체-표현)을 참고한다.

### 객체와 참조의 차이

```java
User user = new User();
```

위 코드에는 두 가지를 구분해서 이해해야 한다.

- `new User()`는 Heap에 `User` 객체를 생성한다.
- `user`는 그 객체를 가리키는 참조를 담는 변수다.
- `user = null;`은 변수에 저장된 참조를 제거하는 것이지, 객체를 직접 삭제하는 명령이 아니다.
- 다른 곳에서 같은 객체를 참조하고 있다면 해당 객체는 계속 도달 가능한 상태다.

> 🔗 참조값 하나가 실제로 몇 바이트를 차지하는지는 [객체 메모리 구조 - Compressed Oops와 압축 참조](./HotSpot%20객체의%20메모리%20구조와%20할당.md#5-compressed-oops와-압축-참조)를 참고한다.

```java
User first = new User();
User second = first; // 같은 객체를 함께 참조

first = null;        // first의 참조만 제거
// second가 객체를 참조하므로 객체는 여전히 도달 가능
```

### GC는 언제 실행될까?

- 객체가 회수 대상이 되었다고 해서 즉시 GC가 실행되는 것은 아니다.
- GC 실행 시점은 JVM과 선택한 가비지 컬렉터, 힙 상태 등에 따라 결정된다.
- `System.gc()`는 GC 실행을 요청하는 힌트일 뿐, 반드시 즉시 GC가 수행된다는 보장은 없다.
- GC가 객체를 회수하더라도 개발자가 객체의 메모리를 직접 반환하는 것은 아니다. 메모리 회수와 재사용은 JVM이 관리한다.

### 자주 혼동하는 용어

| 용어 | 의미 |
|---|---|
| 할당(Allocation) | 객체를 위한 메모리 공간을 확보하는 것 |
| 도달 가능(Reachable) | GC Roots에서 참조를 따라 객체에 도달할 수 있는 상태 |
| 회수 가능(Eligible for GC) | 해당 GC의 판단 기준에서 회수 대상이 될 수 있는 상태 |
| 수집(Collection) | GC가 특정 영역이나 객체 집합을 처리하는 작업 |
| 메모리 반환 | 회수한 공간을 JVM 내부에서 재사용할 수 있도록 만드는 것 |

> 객체가 회수 대상이 되는 것과 실제 메모리가 즉시 운영체제에 반환되는 것은 서로 다른 일이다.

## 1. 객체의 생존과 도달 가능성

**Java의 가비지 컬렉터는 객체가 앞으로 사용될 예정인지 판단하는 것이
아니라, GC Roots에서 해당 객체까지 도달할 수 있는 참조 경로가
존재하는지를 기준으로 생존 여부를 판단한다.**

-   **Reachability Analysis(도달 가능성 분석)**
    -   GC Roots를 시작점으로 객체 참조를 따라가며 도달 가능한 객체를
        탐색하는 방식이다.
    -   객체를 노드(Node), 객체 사이의 참조를 간선(Edge)으로 표현하면
        객체 그래프가 된다.
-   **Strongly Reachable**
    -   GC Roots에서 시작해 강한 참조(Strong Reference)를 따라 도달할 수
        있는 상태다.
    -   일반적인 GC 과정에서 회수 대상이 되지 않는다.
-   **중요한 점**
    -   개발자가 객체를 더 이상 사용하지 않더라도 다른 살아 있는 객체가
        계속 참조하면 회수되지 않는다.
    -   GC는 애플리케이션의 사용 의도를 해석하지 않고 런타임에서 확인할
        수 있는 참조 관계를 기준으로 판단한다.

### 예시: 사용하지 않는 객체가 회수되지 않는 경우

``` java
public class Cache {
    private static final List<Object> CACHE = new ArrayList<>();

    public static void add(Object value) {
        CACHE.add(value);
    }
}
```

-   `CACHE`는 정적 필드를 통해 계속 유지된다.
-   컬렉션에서 객체를 제거하지 않으면 해당 객체는 강한 참조 경로를
    유지한다.
-   애플리케이션에서 더 이상 사용하지 않더라도 GC가 회수할 수 없다.

## 2. GC Roots

**GC Roots는 힙 객체의 도달 가능성을 탐색할 때 출발점이 되는 참조들의
집합이다.**

대표적인 GC Roots의 예시는 다음과 같다. 실제 구성과 탐색 방식은 JVM 구현
및 GC 종류에 따라 달라질 수 있다.

  -----------------------------------------------------------------------
  구분                                설명
  ----------------------------------- -----------------------------------
  Java 스레드의 실행 상태             스택 프레임의 지역 변수, 피연산자
                                      스택 등에 존재하는 객체 참조

  CPU 레지스터                        JIT 컴파일된 코드 실행 중
                                      레지스터에 보관된 객체 참조

  정적 필드                           클래스의 정적 필드가 유지하는 객체
                                      참조

  JNI 참조                            네이티브 코드가 JNI를 통해 유지하는
                                      Java 객체 참조

  JVM 내부 참조                       JVM 런타임이 내부적으로 유지하는
                                      객체 참조
  -----------------------------------------------------------------------

### OopMap과 Safepoint

-   JIT 컴파일된 코드에서는 객체 참조가 반드시 스택에만 존재하는 것은
    아니다.
-   CPU 레지스터에 객체 참조가 보관될 수도 있다.
-   HotSpot은 **OopMap** 등의 정보를 통해 특정 실행 위치에서 객체 참조가
    존재하는 위치를 식별한다.
-   GC는 Safepoint 등 안전한 실행 지점에서 스레드의 참조 정보를 활용해
    루트를 파악할 수 있다.

> 핵심: 힙 내부의 참조만 조사해서는 생존 여부를 판단할 수 없다. 스레드
> 실행 상태와 JVM이 유지하는 참조도 함께 고려해야 한다.

> 🔗 OopMap이 스택·레지스터의 참조 위치를 알려준다면, 힙 객체 내부의 참조 위치는 객체 헤더의 Klass 정보로 파악한다. → [객체 메모리 구조 - 객체 할당과 GC의 관계](./HotSpot%20객체의%20메모리%20구조와%20할당.md#10-객체-할당과-gc의-관계)

## 3. Reference Counting과 순환 참조

**Reference Counting은 객체를 가리키는 참조의 개수를 관리하고, 참조 수가
0이 되면 객체를 회수할 수 있다고 판단하는 방식이다.**

### 동작 방식

-   객체를 가리키는 참조가 추가되면 참조 카운터를 증가시킨다.
-   참조가 제거되면 카운터를 감소시킨다.
-   참조 카운터가 0이 되면 해당 객체를 회수할 수 있다.

### 문제점: 순환 참조

``` text
A ──참조──> B
↑           │
└──참조─────┘

GC Roots에서는 A와 B에 도달할 수 없음
```

-   A는 B를 참조하고, B는 A를 참조한다.
-   외부에서 두 객체를 참조하는 경로가 사라져도 서로를 참조하므로
    카운터는 0이 되지 않는다.
-   참조 카운팅만으로는 이러한 객체들을 회수하기 어렵다.

### Tracing GC와 비교

  -----------------------------------------------------------------------
  구분                    Reference Counting      Tracing GC
  ----------------------- ----------------------- -----------------------
  판단 기준               객체를 가리키는 참조 수 GC Roots에서 도달
                                                  가능한지

  순환 참조               별도 처리 없이는        루트에서 도달할 수
                          회수하기 어려움         없다면 회수 가능

  주요 작업               참조 변경 시 카운터     루트에서 객체 그래프
                          갱신                    탐색

  HotSpot                 주요 GC의 기본 생존     주요 GC가 사용하는 방식
                          판정 방식이 아님        
  -----------------------------------------------------------------------

HotSpot의 주요 가비지 컬렉터는 GC Roots에서 시작하는 도달 가능성 분석을
기반으로 객체의 생존 여부를 판단한다.

## 4. Tri-Color Marking

**Tri-Color Marking은 객체 그래프를 탐색하는 과정을 White, Grey, Black
세 가지 상태로 구분해 설명하는 추상적인 마킹 모델이다.**

  -----------------------------------------------------------------------
  상태                                의미
  ----------------------------------- -----------------------------------
  White                               아직 발견되지 않은 객체

  Grey                                도달 가능한 것으로 발견됐지만 내부
                                      참조를 아직 모두 탐색하지 않은 객체

  Black                               도달 가능한 것으로 확인됐고 내부
                                      참조 탐색도 완료한 객체
  -----------------------------------------------------------------------

### 기본 마킹 흐름

1.  마킹 시작 시 객체들을 White 상태로 간주한다.
2.  GC Roots에서 직접 참조하는 객체를 발견해 Grey로 만든다.
3.  Grey 객체가 참조하는 객체들을 탐색한다.
4.  새로 발견한 객체는 Grey로 표시하고, 탐색을 마친 객체는 Black으로
    표시한다.
5.  더 이상 Grey 객체가 없으면 루트에서 도달 가능한 객체의 탐색이
    완료된다.
6.  해당 마킹 과정에서 발견되지 않은 White 객체는 회수 후보가 된다.

``` text
GC Roots
   |
   v
 Grey 객체
   | 참조 탐색
   v
 White 객체 발견 -> Grey
   |
   v
 내부 참조 탐색 완료 -> Black
```

-   이 세 가지 색상은 이해를 돕기 위한 논리적 상태다.
-   HotSpot이 모든 객체에 White/Grey/Black 값을 직접 저장한다는 뜻은
    아니다.
-   실제 구현은 마킹 비트맵, 작업 큐 등 컬렉터별 자료구조를 활용한다.
-   마킹할 때 객체 내부의 어떤 필드가 참조인지는 객체 헤더가 가리키는 Klass 메타데이터로 파악한다. ([객체 메모리 구조 - Klass Pointer](./HotSpot%20객체의%20메모리%20구조와%20할당.md#4-klass-pointer와-타입-메타데이터))
-   실제 회수 여부는 Reference Processing 등 후속 단계와 컬렉터의
    알고리즘에 따라 결정된다.

## 5. 동시 마킹과 참조 변경 문제

**동시 마킹(Concurrent Marking)은 GC가 객체 그래프를 탐색하는 동안
애플리케이션 스레드도 실행되도록 하는 방식이다. 이때 애플리케이션이 참조
관계를 변경하므로 마킹 결과의 정확성을 보장할 별도 메커니즘이
필요하다.**

애플리케이션에서 객체 그래프를 변경하는 스레드를 **Mutator**라고 부른다.

-   새로운 객체를 생성한다.
-   객체의 필드에 새로운 참조를 저장한다.
-   기존 참조를 다른 참조로 변경하거나 제거한다.

### Tri-Color Invariant가 깨질 수 있는 상황

다음과 같은 상황을 가정한다.

1.  객체 A는 이미 탐색을 완료해 Black 상태다.
2.  객체 B는 아직 발견되지 않아 White 상태다.
3.  Mutator가 A의 필드에 B를 참조하도록 변경한다.
4.  동시에 B를 가리키던 다른 참조가 제거된다.
5.  GC가 Black 객체 A의 참조를 다시 확인하지 않는다면 B를 발견하지 못할
    수 있다.

이 경우 실제로는 도달 가능한 객체 B를 회수 대상으로 잘못 판단할 위험이
있다.

### GC가 고려해야 하는 위험의 비대칭성

-   **살아 있는 객체를 회수하는 경우:** 프로그램의 메모리 안전성과 실행
    정확성을 훼손한다.
-   **죽은 객체를 살아 있다고 판단하는 경우:** 해당 객체의 회수가 늦어져
    메모리 사용량이 일시적으로 증가할 수 있다.

따라서 동시 마킹 알고리즘은 살아 있는 객체를 누락하지 않는 것을
우선한다. 필요하다면 일부 객체를 보수적으로 살아 있는 것으로 취급할 수
있다.

------------------------------------------------------------------------

## 6. G1 GC의 SATB

**G1 GC는 동시 마킹에서 SATB(Snapshot-At-The-Beginning) 알고리즘을
사용한다. SATB는 마킹이 시작된 시점의 논리적인 객체 그래프를 기준으로
생존 집합을 보존하려는 방식이다.**

### SATB의 핵심 개념

-   마킹 시작 시점에 GC Roots에서 도달 가능했던 객체를 기준으로 생존
    집합을 판단한다.
-   마킹 도중 참조 관계가 변경되어 기존 참조 경로가 사라지더라도 필요한
    정보를 추적한다.
-   힙 전체를 별도 공간에 복사하는 실제 스냅샷을 만드는 것은 아니다.

### Pre-Write Barrier를 통한 기존 참조 추적

예를 들어 A의 필드가 B를 참조하고 있다고 가정한다.

``` java
// 변경 전
A.field = B;

// 동시 마킹 중 참조 변경
A.field = C;
```

-   기존에는 A를 통해 B에 도달할 수 있었다.
-   Mutator가 `A.field`를 C로 변경하면 B를 가리키는 참조가 사라진다.
-   이때 G1은 **Pre-Write Barrier**를 통해 덮어쓰기 전의 기존 참조값 B를
    필요한 경우 SATB 버퍼에 기록한다.
-   GC는 버퍼에 기록된 정보를 이용해 마킹 시작 시점의 생존 객체를
    누락하지 않도록 처리한다.

### Floating Garbage

-   마킹 시작 시점에는 도달 가능했지만, 마킹 도중 참조가 변경되어
    실제로는 도달할 수 없게 된 객체가 있을 수 있다.
-   SATB는 마킹 시작 시점의 생존 집합을 보존하므로 이러한 객체를 해당
    마킹 주기에서는 살아 있는 것으로 판단할 수 있다.
-   이처럼 실제로는 더 이상 필요하지 않지만 이번 주기에 회수되지 않은
    객체를 **Floating Garbage**라고 한다.
-   이후 컬렉션에서 다시 평가되어 회수될 수 있다.

> 핵심: SATB는 동시 마킹 중 참조 변경으로 살아 있던 객체를 놓치지 않도록
> 한다. 그 대가로 일부 죽은 객체의 회수가 다음 GC 주기로 미뤄질 수 있다.

------------------------------------------------------------------------

## 7. Write Barrier

**Write Barrier는 애플리케이션이 객체 참조를 변경할 때 JVM이 추가적인
추적 작업을 수행하도록 하는 메커니즘이다.**

-   참조 필드의 쓰기 작업 주변에 JIT 컴파일러나 인터프리터가 필요한
    코드를 배치한다.
-   스레드를 중단시키는 동기화 장벽과 같은 의미가 아니다.
-   GC가 참조 변경을 추적하고 객체 그래프의 정확성을 유지하는 데
    활용한다.

### G1의 두 가지 Write Barrier

  -----------------------------------------------------------------------
  구분                    실행 시점               주요 목적
  ----------------------- ----------------------- -----------------------
  Pre-Write Barrier       기존 참조를 덮어쓰기 전 SATB를 위해 기존
                                                  참조값을 기록

  Post-Write Barrier      새로운 참조를 저장한 후 Card Table을 갱신해
                                                  Region 간 참조 변경
                                                  추적
  -----------------------------------------------------------------------

### Pre-Write Barrier

-   참조를 덮어쓰기 전에 기존 참조값을 확인한다.
-   G1의 SATB 마킹이 활성화된 경우 필요한 기존 참조를 SATB 버퍼에
    기록한다.
-   동시 마킹 중 참조 경로가 사라지는 문제를 다룬다.

### Post-Write Barrier

-   새로운 참조를 저장한 이후 실행된다.
-   서로 다른 Region 사이의 참조 변경을 추적하기 위해 Card Table을
    갱신할 수 있다.
-   Remembered Set을 관리하는 데 필요한 정보를 제공한다.

### 주의할 점

-   Pre-Write Barrier와 Post-Write Barrier는 해결하려는 문제가 다르다.
-   Pre-Write Barrier는 SATB 마킹의 정확성과 관련된다.
-   Post-Write Barrier는 영역 간 참조를 추적해 부분 수집을 효율적으로
    수행하는 것과 관련된다.
-   배리어는 참조 쓰기 경로에 추가 비용을 발생시키므로 GC 성능을 이해할
    때 함께 고려해야 한다.

------------------------------------------------------------------------

## 8. Card Table과 Remembered Set

**Card Table과 Remembered Set은 G1이 일부 Region을 수집할 때 힙 전체를
탐색하지 않고도 다른 Region에서 들어오는 참조를 찾을 수 있도록 돕는
구조다.**

G1은 Java 힙을 여러 개의 Region으로 나누어 관리한다. 특정 Region을
수집하려면 그 Region 외부에서 내부 객체를 참조하는 경로도 확인해야 한다.

> 🔗 객체가 Region 안에 처음 할당되는 과정(TLAB, Bump-Pointer)은 [객체 메모리 구조 - TLAB과 객체 할당 경로](./HotSpot%20객체의%20메모리%20구조와%20할당.md#9-tlab과-객체-할당-경로)를 참고한다.

### Card Table

-   힙을 일정한 크기의 작은 영역인 Card 단위로 나누어 관리한다.
-   참조 필드가 변경되면 Post-Write Barrier가 해당 위치가 속한 Card를
    갱신 대상으로 표시할 수 있다.
-   GC는 변경된 Card 정보를 처리해 영역 간 참조 관계를 추적한다.

### Remembered Set(RSet)

-   특정 Region 외부에서 해당 Region 내부로 들어오는 참조를 찾는 데
    필요한 정보를 관리한다.
-   특정 Region을 수집할 때 다른 Region 전체를 처음부터 탐색하지 않아도
    되도록 돕는다.
-   구현상 Card 기반의 정보와 여러 최적화가 사용되므로, 객체 참조
    하나하나를 정확한 목록으로 저장하는 단순한 자료구조로 이해하면 안
    된다.

### 두 구조의 관계

``` text
Region A                 Region B
+----------------+       +----------------+
| 객체 A1        | ----> | 객체 B1        |
|                |       |                |
| 참조 필드 변경 |       | 수집 대상 가능 |
+----------------+       +----------------+
        |
        v
   Post-Write Barrier
        |
        v
     Card Table
        |
        v
   Remembered Set
        |
        v
Region B 수집 시 외부 참조 확인
```

  -----------------------------------------------------------------------
  구분                                역할
  ----------------------------------- -----------------------------------
  Card Table                          참조 변경이 발생한 힙 영역(Card)을
                                      표시하고 추적

  Remembered Set                      특정 Region으로 들어오는 외부
                                      참조를 찾기 위한 정보 관리

  Post-Write Barrier                  참조 저장 이후 Card 정보 갱신 등에
                                      관여
  -----------------------------------------------------------------------

> 핵심: SATB가 동시 마킹 중 기존 참조가 사라지는 문제를 다룬다면, Card
> Table과 Remembered Set은 Region 단위 수집에서 영역 간 참조를
> 효율적으로 찾는 문제를 다룬다.

## 9. Reference Processing

**Java는 Strong Reference 이외에도 SoftReference, WeakReference,
PhantomReference를 제공하며, GC는 각 참조 유형의 규칙에 따라 참조 대상을
별도로 처리할 수 있다.**

  -----------------------------------------------------------------------
  참조 유형               특징                    주요 용도 및 주의점
  ----------------------- ----------------------- -----------------------
  Strong Reference        일반적인 객체 참조.     일반적인 객체 사용
                          강하게 도달 가능한      
                          객체를 유지             

  SoftReference           메모리 상황에 따라 참조 메모리에 민감한 캐시
                          대상이 제거될 수 있음   등에 활용 가능. 제거
                                                  시점을 정확히 제어할 수
                                                  없음

  WeakReference           강한 참조나 소프트 참조 WeakHashMap 등
                          등으로 도달할 수 없으면 
                          GC가 참조를 제거할 수   
                          있음                    

  PhantomReference        `get()`으로 참조 대상   ReferenceQueue를 통한
                          객체를 얻을 수 없음.    정리 작업 연계
                          객체의 정리 단계와 연계 
  -----------------------------------------------------------------------

### WeakReference 예시

``` java
Object object = new Object();
WeakReference<Object> weak = new WeakReference<>(object);

object = null;

// 이후 GC가 실행되면 weak 참조 대상이 제거될 수 있다.
```

-   `WeakReference` 자체가 객체를 강하게 유지하지 않는다.
-   다른 강한 참조가 없다면 GC가 참조 대상을 제거할 수 있다.
-   실제 GC 실행 시점은 보장되지 않는다.

### PhantomReference와 Cleaner

-   `PhantomReference`의 `get()`은 항상 `null`을 반환한다.
-   참조 대상 객체가 정리 단계에 도달했는지 ReferenceQueue 등을 통해
    확인하는 데 사용한다.
-   실제 애플리케이션에서는 직접 PhantomReference를 관리하기보다
    `Cleaner` 같은 상위 API를 사용할 수 있다.

### Reference Processing

GC는 참조 대상의 도달 가능성과 참조 유형에 따라 참조를 처리한다.

-   참조를 제거한다.
-   필요한 경우 ReferenceQueue에 참조 객체를 등록한다.
-   참조 유형에 따른 후속 정리 작업과 연계한다.

## 10. Java 메모리 누수

**Java에서도 더 이상 사용하지 않는 객체가 강한 참조 경로를 유지하면 GC가
회수하지 못하는 메모리 누수가 발생할 수 있다.**

GC는 도달 불가능한 객체를 회수할 수 있지만, 불필요한 참조가 남아 있는
객체까지 사용 의도를 파악해 제거하지는 않는다.

### 대표적인 원인

  -----------------------------------------------------------------------
  원인                    발생 상황               대응 방법
  ----------------------- ----------------------- -----------------------
  전역 컬렉션             정적 컬렉션에 객체를    사용이 끝난 객체 제거,
                          계속 추가하고 제거하지  크기 제한 및 만료 정책
                          않음                    적용

  캐시                    캐시 항목이 무한정 쌓임 최대 크기, TTL, 퇴출
                                                  정책 적용

  이벤트 리스너           등록한 리스너를         사용 종료 시 등록 해제
                          해제하지 않음           

  콜백                    완료된 작업의 콜백      작업 종료 후 참조 정리
                          참조가 계속 유지됨      

  ThreadLocal             스레드 풀의 장수명      사용 후 `remove()` 호출
                          스레드가 값을 계속 보유 
  -----------------------------------------------------------------------

### ThreadLocal 주의점

-   `ThreadLocalMap`의 키는 `ThreadLocal`에 대한 약한 참조를 사용한다.
-   값은 강한 참조로 유지된다.
-   키가 GC 대상이 되더라도 값이 즉시 제거된다고 보장할 수 없다.
-   스레드 풀처럼 오래 살아 있는 스레드에서는 값이 오랫동안 남을 수
    있다.

``` java
private static final ThreadLocal<String> CONTEXT = new ThreadLocal<>();

public void process() {
    try {
        CONTEXT.set("request-context");
        // 작업 수행
    } finally {
        CONTEXT.remove();
    }
}
```

> 핵심: GC가 정상적으로 동작해도 애플리케이션이 불필요한 참조를 계속
> 유지하면 메모리 사용량은 증가한다. 메모리 누수 분석에서는 객체의
> 생성량뿐 아니라 객체를 유지하는 참조 경로를 확인해야 한다.

## 11. 운영 환경에서의 GC 관찰

**힙 사용량이 증가할 때는 GC 횟수만 확인하지 말고, GC 이후에도 살아남는
객체의 양과 참조 경로를 함께 분석해야 한다.**

### 확인할 지표

  -----------------------------------------------------------------------
  지표                                확인 목적
  ----------------------------------- -----------------------------------
  객체 할당률(Allocation Rate)        객체가 얼마나 빠르게 생성되는지
                                      확인

  GC 이후 힙 사용량                   회수 후에도 유지되는 생존 객체의
                                      크기 확인

  Old Generation 점유율               장기간 살아남는 객체가 증가하는지
                                      확인

  GC 일시 중지 시간(Pause Time)       애플리케이션이 GC로 인해 중단되는
                                      시간 확인

  동시 마킹 소요 시간                 마킹 작업에 드는 시간 확인

  Reference Processing 시간           특수 참조 처리 비용 확인
  -----------------------------------------------------------------------

> 🔗 할당률(Allocation Rate)이 어떤 경로로 만들어지는지, JFR·JOL로 무엇을 관찰할 수 있는지는 [객체 메모리 구조 - 운영 환경에서의 관찰](./HotSpot%20객체의%20메모리%20구조와%20할당.md#11-운영-환경에서의-관찰)을 참고한다.

### Heap Dump

힙 덤프를 분석하면 다음 정보를 확인할 수 있다.

-   객체별 개수와 메모리 사용량
-   객체 사이의 참조 관계
-   특정 객체를 유지하고 있는 참조 경로
-   메모리를 많이 차지하는 객체와 컬렉션

### Dominator Tree와 Retained Size

-   **Dominator Tree**
    -   객체 그래프에서 특정 객체가 다른 객체들의 도달 가능성을 지배하는
        관계를 분석한다.
    -   어떤 객체가 다른 많은 객체를 계속 유지하고 있는지 찾는 데
        유용하다.
-   **Retained Size**
    -   특정 객체가 더 이상 유지되지 않을 때 함께 회수될 수 있는
        객체들의 메모리 크기를 고려한 값이다.
    -   단순히 해당 객체 자체의 크기인 Shallow Size와 구분된다.
    -   Shallow Size는 헤더 + 필드 + 패딩으로 결정된다. → [객체 메모리 구조 - 필드 배치와 메모리 정렬](./HotSpot%20객체의%20메모리%20구조와%20할당.md#6-필드-배치와-메모리-정렬)

### GC Log

G1 환경에서는 Unified Logging을 통해 GC 단계별 정보를 확인할 수 있다.

``` bash
-Xlog:gc*
```

상황에 따라 로그 수준과 태그를 조정해 Concurrent Mark, Remark, Reference
Processing, Remembered Set 관련 작업을 분석할 수 있다.

-   상세 로그는 출력량과 운영 비용을 증가시킬 수 있다.
-   장애 분석 목적에 맞춰 필요한 수준으로 설정하는 것이 좋다.
-   GC가 자주 실행된다는 사실만으로 메모리 누수라고 판단해서는 안 된다.

## 12. 전체 흐름 요약

### 객체 생존 판단부터 회수까지

1.  **GC Roots 확인**
    -   스레드 스택, 정적 필드, JNI 참조, JVM 내부 참조 등 시작점을
        확인한다.
2.  **Reachability Analysis**
    -   GC Roots에서 강한 참조를 따라 도달 가능한 객체를 탐색한다.
3.  **Marking**
    -   도달 가능한 객체를 마킹한다.
    -   Tri-Color Marking은 이 과정을 설명하는 대표적인 추상 모델이다.
4.  **Concurrent Marking**
    -   애플리케이션과 GC가 동시에 실행되면 참조 관계가 변경될 수 있다.
5.  **Write Barrier**
    -   참조 변경을 추적해 마킹 정확성과 영역 간 참조 정보를 유지한다.
6.  **Reference Processing**
    -   SoftReference, WeakReference, PhantomReference 등의 규칙에 따라
        참조를 처리한다.
7.  **회수**
    -   컬렉터별 알고리즘에 따라 회수 가능한 객체의 메모리를 확보한다.

### G1 GC 핵심 개념 비교

  -----------------------------------------------------------------------
  개념                    해결하려는 문제         핵심 역할
  ----------------------- ----------------------- -----------------------
  SATB                    동시 마킹 중 기존 참조  마킹 시작 시점의 논리적
                          경로가 사라지는 문제    생존 집합 보존

  Pre-Write Barrier       참조를 덮어쓰면서 기존  기존 참조값을 SATB
                          참조가 사라지는 문제    버퍼에 기록

  Post-Write Barrier      Region 사이의 참조 변경 Card Table 갱신 등에
                          추적                    관여

  Card Table              변경된 힙 영역을        Card 단위로 참조 변경
                          효율적으로 추적         위치 표시

  Remembered Set          특정 Region 외부에서    부분 수집 시 필요한
                          들어오는 참조 확인      외부 참조 정보 제공

  Reference Processing    강한 참조 이외의 참조   참조 유형에 따른 제거
                          유형 처리               및 큐 등록
  -----------------------------------------------------------------------

### 최종 정리

1.  **GC는 객체의 사용 의도가 아니라 도달 가능성을 기준으로 생존 여부를
    판단한다.**
2.  **GC Roots는 객체 그래프 탐색의 시작점이며, 힙 외부의 실행 상태와
    JVM 내부 참조도 고려한다.**
3.  **Tracing GC는 루트에서 도달할 수 없는 순환 참조 객체도 회수할 수
    있다.**
4.  **동시 마킹 중에는 Mutator가 참조 관계를 변경하므로 Write Barrier
    등의 추적 메커니즘이 필요하다.**
5.  **G1의 SATB는 마킹 시작 시점의 논리적인 객체 그래프를 보존하며,
    Floating Garbage가 발생할 수 있다.**
6.  **Card Table과 Remembered Set은 Region 단위 수집에서 영역 간 참조를
    효율적으로 찾도록 돕는다.**
7.  **Java에서도 불필요한 강한 참조가 남아 있으면 메모리 누수가 발생할
    수 있으므로, 힙 사용량뿐 아니라 참조 경로를 분석해야 한다.**

## 13. 이해를 돕는 간단한 예시

### 예시 1. 참조가 끊기면 회수 대상이 될 수 있다

```java
public class Main {
    public static void main(String[] args) {
        User user = new User();
        user = null;
    }
}
```

- `new User()`로 객체가 Heap에 생성된다.
- `user`가 객체를 참조하므로 처음에는 도달 가능하다.
- `user = null` 실행 후 다른 참조가 없다면 객체는 도달 불가능해질 수 있다.
- 이후 GC가 수행되면 해당 객체는 회수 대상이 될 수 있다.

주의: `null`을 대입했다고 즉시 메모리가 회수되는 것은 아니다.

### 예시 2. 참조가 남아 있으면 사용하지 않아도 회수되지 않는다

```java
public class UserCache {
    private static final List<User> CACHE = new ArrayList<>();

    public static void main(String[] args) {
        User user = new User();
        CACHE.add(user);

        user = null;
        // 지역 변수 user는 참조를 놓았지만 CACHE가 객체를 계속 참조한다.
    }
}
```

참조 관계를 단순화하면 다음과 같다.

```text
GC Roots
   |
   v
UserCache.CACHE (static)
   |
   v
List
   |
   v
User 객체
```

- 지역 변수 `user`가 참조를 놓아도 컬렉션에 저장된 참조는 남아 있다.
- 따라서 User 객체는 GC Roots에서 도달 가능하다.
- 캐시에서 객체를 제거하거나 적절한 만료 정책을 적용해야 한다.

### 예시 3. 서로 참조해도 외부에서 도달할 수 없으면 회수 대상이다

```java
class Node {
    Node next;
}

public class Main {
    public static void main(String[] args) {
        Node a = new Node();
        Node b = new Node();

        a.next = b;
        b.next = a;

        a = null;
        b = null;
    }
}
```

실행 후 참조 관계는 객체끼리만 연결되어 있다.

```text
A ─────> B
^        |
|________|

GC Roots에서 A 또는 B로 가는 경로 없음
```

- A와 B는 서로를 참조하지만 GC Roots에서 도달할 수 없다.
- Tracing GC는 루트에서 탐색하므로 두 객체 모두 회수 대상으로 판단할 수 있다.
- 이것이 참조 카운팅 방식에서 문제가 되는 순환 참조와 다른 점이다.

### 예시 4. ThreadLocal 값 정리하기

```java
private static final ThreadLocal<String> USER_CONTEXT = new ThreadLocal<>();

public void handleRequest() {
    try {
        USER_CONTEXT.set("user-123");
        // 요청 처리
    } finally {
        USER_CONTEXT.remove();
    }
}
```

- 스레드 풀의 스레드는 여러 요청에서 재사용될 수 있다.
- `ThreadLocal` 값을 설정한 뒤 제거하지 않으면 스레드가 값을 계속 유지할 수 있다.
- `finally`에서 `remove()`를 호출하면 정상 처리와 예외 발생 상황 모두에서 정리할 수 있다.

### 예시 5. G1 SATB에서 기존 참조를 기록하는 이유

마킹 시작 시점에 A가 B를 참조하고 있다고 가정하자.

```text
마킹 시작 시점

GC Roots -> A -> B
```

동시 마킹 중 애플리케이션이 참조를 변경한다.

```java
A.field = C; // 기존 B 참조를 C로 변경
```

변경 후 객체 그래프만 보면 다음과 같다.

```text
GC Roots -> A -> C

B로 가는 경로가 사라짐
```

- 마킹 시작 시점에 B는 살아 있는 객체였다.
- 하지만 참조 변경만 보고 마킹하면 B를 놓칠 수 있다.
- G1의 SATB Pre-Write Barrier는 덮어쓰기 전 기존 참조 B를 필요한 경우 기록한다.
- GC는 기록된 정보를 바탕으로 마킹 시작 시점의 생존 집합을 놓치지 않도록 한다.
- 이 때문에 B가 실제로는 더 이상 필요하지 않더라도 이번 마킹 주기에는 회수되지 않을 수 있다. 이를 Floating Garbage라고 한다.

## 💡 기억해야 할 핵심

-   **GC Roots:** 객체 그래프 탐색의 출발점
-   **Reachability:** GC Roots에서 객체까지 도달할 수 있는지
-   **Tri-Color Marking:** White / Grey / Black으로 설명하는 마킹 모델
-   **Mutator:** 애플리케이션 객체 그래프를 변경하는 실행 주체
-   **SATB:** 마킹 시작 시점의 논리적 생존 집합을 보존하는 G1의 동시
    마킹 방식
-   **Pre-Write Barrier:** 덮어쓰기 전 기존 참조 추적
-   **Post-Write Barrier:** 저장 후 영역 간 참조 변경 추적
-   **Card Table:** 변경된 힙 영역(Card) 표시
-   **Remembered Set:** 특정 Region으로 들어오는 외부 참조 정보 관리
-   **Floating Garbage:** 이번 마킹 주기에서 살아 있는 것으로 판단되어
    회수가 미뤄진 객체
-   **Memory Leak:** 불필요한 참조가 유지되어 객체가 회수되지 않는 현상
